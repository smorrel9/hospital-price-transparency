## Recurring maintenance (no fixed schedule -- just don't forget this exists)

**Source URL freshness.** Most hospitals in `data/hospitals.json` use plain static URLs (MD Anderson, Houston Methodist, BSW, Ascension) that don't expire. A few -- St. David's being the first confirmed case -- use signed URLs with a time limit instead. Any hospital on a signed-URL vendor is a candidate for silently going stale. Worth periodically re-running `hospital-discovery` across the whole manifest (not just new hospitals) to catch this before it's needed urgently, rather than discovering it mid-onboarding like this time.

**CMS annual refresh.** Per `database-architecture.md`'s original roadmap note: CMS files update roughly annually. `data/hospitals.json` doesn't yet track `last_modified` from the source (only `last_fetched_at`), so there's no automated way to tell "this hospital's file has a newer version available" vs. "nothing's changed." **Confirmed happening in practice, not just theoretical:** BSW's row count differed between two `fetch-data` runs eight-ish hours apart (877,867 vs. 934,716 seeded rows) with identical parsing code both times -- the only explanation is the hospital's published file itself changed in between. Worth adding version/`last_modified` tracking if/when this pipeline runs on more than a handful of hospitals, so a changed source is a visible event, not a silent row-count drift someone has to notice by accident.
